# إعداد Supabase مخصص للأهرام — مرحلة القبول النهائي

## الحالة الحالية
- مشروع GitHub المرجعي: `abadry1902/Ahram-platform`، فرع `main` (تمت مراجعته بتاريخ 2026-10-25).
- الملفات الستة تحت `supabase/migrations` موجودة في المستودع؛ **لم تُنفَّذ من خلال هذه الحزمة**.
- اتصال Masterframe 01 موصول الآن، والمشروع الموجود `masterframe 01` (`tfidmxlaugqcwskanmxk`) سليم وفارغ من جداول التطبيق والترحيلات. لم ننشئ مشروعًا أو ندخل مفاتيح أو نكتب سجلات فيه.
- غرضه كبيئة QA لم يُعتمد بعد؛ لا تعتبر توصيل الحساب موافقة على تحويل مشروع إنتاج إلى قاعدة اختبار.
- الترحيلات الستة عُدّلت قبل أول تطبيق لمعالجة UID والمنح، ونجحت محليًا عبر `npm run test:db-security`؛ راجع البنود المتبقية في تقرير الأمان.
- لا تستخدم مشروع EgyToys أو أي مشروع يحتوي بيانات عملاء حقيقية.

## خطوات صاحب المشروع / المنفذ المعتمد
1. اعتمد غرض المشروع الموجود داخل **masterframe-01 Org**: QA ببيانات وهمية أم إنتاج. إن كان للإنتاج، يلزم مشروع QA منفصل مع موافقة التكلفة قبل إنشائه. لا تنشئ مشروعًا آخر إذا كان الموجود معتمدًا للاختبار.
2. راجع migrations أمنيًا قبل تشغيلها، خاصة وظائف `SECURITY DEFINER` و`GRANT EXECUTE` وRLS. لا تنفذ SQL تلقائيًا على Production. لا تستخدم نسخ الترحيلات السابقة للإصلاح، ولا تعِد تشغيل ملفات تاريخية معدلة على قاعدة سبق ترحيلها.
3. نفذ ملفات المشروع الستة بالترتيب، بعد المراجعة، على مشروع QA فقط:
   - `202610240001_initial.sql`
   - `202610240002_attachments.sql`
   - `202610240003_reminders_review.sql`
   - `202610240004_personal_status.sql`
   - `202610240005_template_creation.sql`
   - `202610240006_review_feedback.sql`
4. اضبط Auth وSMTP ودعوات الموظفين، وأوقف التسجيل العام للموظفين. لا تشارك كلمات المرور عبر GitHub.
5. أنشئ أربعة حسابات اختبار **وهمية** منفصلة: مشرف، موظف A، موظف B، محرر محتوى.
6. بعد التحقق من UUID الحسابات عبر لوحة Auth، عدّل أدوار ملفاتهم عبر SQL Editor بصلاحية المسؤول: المشرف `supervisor`، الموظفان `employee`، المحرر `content_editor`. **لا تسمح لأي عميل بتعديل `profiles.role`**.
7. تأكد من تطابق أسماء المستخدمين مع الأدوار بواسطة استعلام read-only: `select id, role from public.profiles where id in (...);` (استبدل UUIDs التي تحققت منها).
8. شغّل الاستعلامات في `docs/acceptance/read-only-audit.sql` وراجع نتائجها قبل الاختبار.
9. انسخ `.env.qa.example` إلى `.env.qa.local` داخل المشروع محليًا. ضع رابط مشروع QA ومفتاحه العام وبيانات **اختبار فقط**؛ لا تضف service role إلى هذا الملف.
10. شغّل الاختبار غير المُغيِّر للبيانات أولًا:

```bash
node --version # يتطلب Node 20.6+؛ يفضل Node 22+
node --env-file=.env.qa.local scripts/qa/01_auth_rls_readonly.mjs
```

11. بعد الموافقة على إنشاء بيانات وهمية داخل QA **فقط**، اضبط `QA_MUTATION_CONFIRM=YES_DISPOSABLE_QA_ONLY` في `.env.qa.local`، ثم شغّل:

```bash
node --env-file=.env.qa.local scripts/qa/02_role_operations_mutating.mjs
```

12. احفظ تقرير الاختبار (لا تشارك رموز جلسات أو كلمات مرور)، راجع عناصر القبول في `docs/acceptance`، ثم نفّذ اختبارات المتصفح يدويًا من حسابات منفصلة.

## ملاحظات مهمة
- سكربت الاختبارات المعدلة ينشئ بيانات اختبار بعنوان `QA-AHRAM-...` وقد تبقى في قاعدة QA؛ لا تشغله على الإنتاج.
- أي بيانات أو أرقام أو لقطات شاشة تجريبية **ليست دليلًا** على تكامل الإنتاج.
- يجب استكمال MFA، rate limiting، CAPTCHA، فحص المرفقات، النسخ الاحتياطي والاستعادة، مراقبة الأخطاء وسياسة الاحتفاظ قبل التعامل مع بيانات حقيقية.
- ملف `.env.qa.local` يُحفظ خارج GitHub أو يضاف إلى `.gitignore`، ولا يرسل لأحد.
- إذا لم تتوفر صلاحية حساب Supabase المخصص، أوقف الخطوات التي تتطلبه واطلب توصيل الحساب المعتمد.

## ملاحظة المراجعة الحالية
قبل تطبيق الترحيلات اقرأ `source-security-review.md`. مراجعة المصدر رصدت بنودًا تحتاج معالجة/حسم قبل SQL، ولم تُنفذ الترحيلات على أي قاعدة. لا تعتمد دليل الإعداد باعتباره موافقة على الإنشاء أو التكلفة.
اختبار القراءة لا يكتب سجلات الأعمال، لكنه يسجّل الدخول فعليًا، وبالتالي ينشئ جلسات وأحداث مصادقة. يجب تعريف `QA_PROJECT_PURPOSE=AL_AHRAM_DISPOSABLE_QA` بعد التحقق من المشروع وموافقة المالك.
