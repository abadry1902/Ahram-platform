# حدود الاختبارات البرمجية

- الاختبارات تقيس سلوك REST وRPC بأربع جلسات حقيقية، ولا تمثل اختبار اختراق شاملًا.
- سكربت القراءة لا يغير سجلات الأعمال؛ تسجيل الدخول ينشئ جلسات وأحداث مصادقة. سكربت العمليات ينشئ بيانات وهمية ولا يحذفها تلقائيًا، ويحتاج تصريح `QA_MUTATION_CONFIRM=YES_DISPOSABLE_QA_ONLY` وتطابق project ref.
- يجب مراجعة كل نتيجة PASS/FAIL ومقارنتها بإعدادات RLS الفعلية. النسخة المراجعة لا تقبل 500 أو 404 أو خطأ JWT كمنع صحيح؛ يلزم صفوف مفلترة أو كود صلاحيات/حارس معروف. أما العمليات الإيجابية فتتطلب نجاحًا وظهور الصفوف.
- لا تشمل السكربتات تلقائيًا اختبار تدفق دعوات البريد أو MFA أو صلاحيات التخزين للروابط الموقعة أو CAPTCHA أو فحص الفيروسات أو تجديد الجلسات في المتصفح؛ هذه اختبارات يدوية/مستقلة لازمة للقبول.
- اختبارات anon تستخدم الآن فلاتر صريحة للمقالات غير المنشورة والروابط المخفية؛ غياب البيانات وحده لا يثبت RLS، ولذلك يلزم اختبار العمليات ببيانات موجبة وممنوعة معًا.
- لا تنسخ لقطات أو بيانات QA إلى الإنتاج.

- اسم المشروع وإعلان الغرض لا يستطيعان إثبات أن القاعدة QA. التحقق من الملكية والغرض وموافقة المالك يسبقان أي تشغيل.
- اختبارات helper المحلية تختبر سلامة الاختبارات نفسها فقط، ولا تثبت RLS أو صلاحيات قاعدة حقيقية.
